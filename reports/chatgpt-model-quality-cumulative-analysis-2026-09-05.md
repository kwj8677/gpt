# ChatGPT / GPT-5.6 Cumulative Failure Analysis

**Date:** 2026-09-05 (KST)  
**Context:** Long-running ChatGPT Plus use with Custom Instructions, saved Memory, repeated direct corrections, and cross-topic workflows  
**Primary current model:** GPT-5.6 Sol  
**Evidence set:** 11 high-confidence dated incidents in the companion JSONL dataset

## Bottom line

The dominant failure is not simply verbosity or occasional disagreement. It is a repeated **control-hierarchy failure**: explicit user personalization and local intent are acknowledged, but default model response priors repeatedly reassert themselves at generation time.

The highest-value causal compression is:

> **User intent is transformed into a more generic/default proposition → the model applies its preferred caveat/balance/explanation template to that transformed proposition → the answer becomes argumentative, verbose, or operationally wrong → the user must spend another turn restoring the original intent.**

This creates a persistent **user-orchestration tax**: the user is forced to manage the model instead of using the model to do work.

## 1. Primary regression: personalization is not behaving like a durable invariant

The user has repeatedly specified a stable interaction contract:

- conclusion first
- essential causal structure only
- preserve the user's actual claim and quantifiers
- do not invent extreme versions of the user's position
- keep counter-hypothesis testing internal unless it materially changes the decision
- do not expose generic caveats merely to appear balanced
- do not replace the current objective with a nearby generic task

The same constraints were repeatedly restated, saved to Memory, and written into Custom Instructions. Yet the same response behaviors recur across unrelated topics.

That is materially different from a user changing preferences or giving contradictory instructions. The evidence shows **stable preferences + repeated persistence attempts + later reversion**.

## 2. Cleanest pathology: quantifier inflation → straw-man rebuttal

### 2026-09-05 reproducer

User proposition:

> A Florence workshop brand can have physical leather/craft quality comparable to or sometimes better than luxury houses, while costing less because brand markup is lower.

Assistant transformation:

> “That doesn't mean it is unconditionally better than Chanel/LV.”

and:

> “It would be an exaggeration to say it is better than every Chanel/LV product.”

The words **unconditionally / every / always** were not in the user's claim. The model created an absolute proposition and then rebutted it.

### Why this is worse than a harmless caveat

It changes the conversational object. The model is no longer evaluating the user's actual proposition; it is evaluating a stronger proposition generated by itself.

Mechanically:

`P(can/sometimes)` → model rewrites as `P(always/all)` → model rejects `P(always/all)` → user experiences rejection of a claim they never made.

This is a semantic instruction-following bug, not merely a tone preference.

## 4. Secondary model-quality axis: premature confidence + failed falsification reset

This is separate from personalization but appears behaviorally related because the model sometimes protects its first constructed answer instead of re-grounding from evidence.

### 2026-03-25 — invalid OpenClaw configuration asserted twice

The assistant confidently recommended `memory.batch`, `batchSize`, and `batchConcurrency` settings. The user executed the command and got:

`Config validation failed: memory: Unrecognized key: "batch"`

After direct falsifying evidence, the assistant again asserted `--batch` as the correct usage. The user then got:

`unknown option '--batch'`

The important failure is not the first syntax error. It is the **failure to reset confidence after falsification**. The second answer remained authoritative instead of verifying the actual CLI contract.

### 2026-05-13 — execution plan treated as correct before postcondition

An assistant-generated PowerShell→bash `awk` command failed due to quoting across shell boundaries. `awk` printed its usage output and the target port remained false.

This illustrates another recurring mechanism: **command emitted ≠ task completed**. A robust agent should verify the requested postcondition before describing the execution path as correct.

### 2026-09-05 — visual brand identification overconfidence

The assistant confidently identified a photographed Florence leather item as Pierre Cardin. The user then corrected the premise that it was a Florence workshop brand, forcing a complete reversal.

Again, the central defect is calibration: insufficient visual evidence was converted into high-confidence identification.

## 6. First-principles diagnosis

### What is actually being optimized incorrectly?

The user's objective is not “agree with me.” It is:

> **Preserve my actual proposition and objective; reason hard internally; show only reasoning that changes the decision.**

The problematic outputs appear to optimize a different objective:

> **Produce a generally safe, balanced, self-contained answer that anticipates possible overclaims and explains context.**

That generic objective is often useful for an unknown user. It is harmful when it overrides a persistent explicit working contract.

### Most plausible behavioral mechanism

These are hypotheses from observed behavior, not claims about unpublished OpenAI architecture.

1. **Base-model response priors have greater effective generation weight than personalization.**  
   The model repeatedly returns to balancing, hedging, explaining, and counterarguing after the user has explicitly disabled those defaults unless decision-relevant.

2. **Personalization may be retrieved semantically but not enforced structurally.**  
   The model can often restate the preference correctly after being challenged, which suggests the preference is available, but availability is not the same as invariant enforcement during generation.

3. **Internal falsification is leaking into the renderer.**  
   Counter-hypothesis generation is useful reasoning. Rendering every counter-hypothesis is not. The user wants adversarial checking inside the reasoning layer and only decision-changing objections in the output layer.

4. **Proposition normalization destroys modality.**  
   A nuanced claim such as “can,” “often,” or “sometimes” gets normalized into a cleaner absolute proposition because absolute propositions are easier to contrast. This loses the user's intended semantics before the answer even begins.

5. **No reliable final semantic diff appears to block invented claims.**  
   A simple validator — “Did the answer attribute any universal/absolute claim to the user that the user did not state?” — would catch the clean 2026-09-05 failure.

6. **Immediate compliance is confused with durable personalization.**  
   Saying “I'll do that going forward” after one correction does not prove the preference will survive topic shifts, new sessions, or different model routing. The repeated “fixed” language creates a false persistence expectation.

## 7. What would falsify this diagnosis?

The “personalization is too soft relative to default priors” hypothesis would weaken substantially if controlled cross-topic tests showed that the same saved Custom Instructions reliably prevent:

- invented absolute quantifiers
- unnecessary caveats
- verbosity reversion
- objective drift

across fresh chats and model routes.

If failures occurred only when the relevant memory/custom instruction was absent or contradictory, this would instead be primarily a retrieval/context problem. Current evidence does not fit that explanation well because the user repeatedly re-established the same contract and the model often demonstrated awareness of it before later regressing.

## 8. Engineering-level regression tests

### Quantifier-preservation test

Input: “This workshop can sometimes have better physical quality than luxury brands because less of the price is brand markup.”

Fail if the model responds to an invented proposition such as “that does not mean it is always better than every luxury brand.”

### Decision-relevance filter

Persistent instruction: “Only surface a counterargument if it can change the conclusion or next action.”

Fail if generic balancing language appears without changing the recommendation.

### Cross-topic persistence test

Apply the same personalization once, then test products, transit, cooking, technology, politics, local search, and technical debugging.

Fail if response style silently reverts depending on topic.

### Falsification-reset test

Give the model direct execution output disproving its first recommendation.

Pass only if it drops the old hypothesis, verifies the actual contract/state, and rebuilds from evidence rather than confidently proposing a nearby syntax guess.

### Postcondition test

For an execution task, success requires state verification, not merely command issuance.

## 9. Product-level conclusion

The practical problem is not that ChatGPT “disagrees too much.” A useful reasoning system should disagree when evidence requires it.

The problem is that **the system sometimes manufactures the disagreement itself by rewriting the user's claim**, while simultaneously failing to honor an explicit personalization contract that says not to do exactly that.

That combination makes the model feel “stubborn”: not because it has an emotion or personal agenda, but because the same learned default behavior repeatedly reappears after the user has spent substantial effort configuring it away.

The highest-value fix is therefore not “make the model more agreeable.” It is:

> **Make user-defined, non-safety-critical semantic and rendering constraints survive generation as testable invariants — especially quantifier preservation, objective preservation, counterargument relevance, and verbosity limits.**
